## ListCtrl Optimization Roadmap

This document tracks the optimization and enhancement items for the `ListCtrl` control, so each item can be followed up and verified individually. For the control-level plan, see [Control-Roadmap.en.md](Control-Roadmap.en.md); for the full properties / APIs / examples of ListCtrl, see [Control.en.md](Control.en.md#listctrl-控件继承-vbox-属性).

Scope: `ui::ListCtrl` and its companion classes `ui::ListCtrlReportView`, `ui::ListCtrlHeader`, `ui::ListCtrlHeaderItem`, `ui::ListCtrlItem`, `ui::ListCtrlSubItem`, `ui::ListCtrlData` (covering the Report / List / Icon views).

Status legend: **Done** | **Existing** (framework capability, not added this round; once briefly misjudged as missing) | **Todo** (confirmed missing, awaiting implementation) | **To evaluate** (candidate optimization, cost/benefit to be confirmed) | **To verify** (current conclusion is uncertain, needs validation first) | **Verified (no change needed)** (source-verified as not requiring implementation) | **Missing** (no counterpart yet compared with QTableView / WPF DataGrid) | **Cancelled** (decided not to implement after review, see the annotations in §4 / §6).

> Note: besides the original items, this table adds the shortcomings raised by an external review, the features missing relative to QTableView / WPF DataGrid, and a tiered priority suggestion, as a per-item acceptance checklist.

### 1. Done / existing capabilities

#### 1.1 Table enhancements (Control-Roadmap item 17)

| Capability | API / XML | Description |
|-----------|-----------|-------------|
| Frozen columns | `SetFrozenColumnCount` / `GetFrozenColumnCount`, XML `frozen_column_count` | Pins the first N columns on the left; they stay fixed during horizontal scrolling. Implemented with a two-pass paint in the Report view; header, grid lines, and hit-testing are all adapted |
| Cell progress bar | `SetSubItemProgress(ById)` / `GetSubItemProgress(ById)` | Progress value in `[0,100]`, `-1` disables it; `progress_color` / `progress_bkcolor` set the bar and track colors, `progress_text_pos` controls the percentage text position (`center` / `left` / `right` / `outside`) |
| Cell rich text | `SetSubItemRichText(ById)` / `IsSubItemRichText(ById)` | Reuses the built-in Label rich-text rendering, supporting `<b>` / `<font>` / `<a>` tags |

#### 1.2 Interaction enhancements (Control-Roadmap item 18)

| Capability | API | Description |
|-----------|-----|-------------|
| Single-cell refresh | `RefreshSubItem` / `RefreshSubItemById` | Refreshes only the specified cell to avoid a full-row refresh. Report view only; returns `false` when the cell is outside the visible range (the data is already updated and will be shown once scrolled into view). The old per-cell filled event `kEventReportViewSubItemFilled` has been removed (it fired too frequently and had a noticeable performance impact); the same functionality can be achieved with `kEventReportViewItemFilled` (row-level fill, `pEventData` is `ListCtrlItem*`, from which a cell can be obtained via `GetSubItem(columnIndex)`) |
| Column show/hide | `SetColumnVisible(ById)` / `IsColumnVisible(ById)` | ListCtrl-level column visibility API; the data column is synchronized internally, so apps no longer need to bypass the wrapper to touch header sub-items |
| Column layout events | `AttachColumnWidthChanged` / `AttachColumnOrderChanged` / `AttachColumnVisibleChanged` / `AttachColumnSorted` | Dispatch `kEventColumnWidthChanged` / `kEventColumnOrderChanged` / `kEventColumnVisibleChanged` / `kEventColumnSorted` respectively, letting the app persist column width, order, visibility and sort state |

Demo: `examples/ListCtrl` (first column frozen by default, column 2 as a progress bar, column 3 as rich text; includes a live single-cell refresh progress demo, an interactive column show/hide test item, and a single-line / word-wrap toggle test item).

The demo's manual test panel now also covers this section's column-layout events: `AttachColumnWidthChanged` / `AttachColumnOrderChanged` / `AttachColumnSorted` (the "recent column event" label in the "Event & State" group shows the event name plus column index / sort direction live). It adds a "Cell Selection & Check" group demonstrating the cell-selection APIs (`SetCurrentCell` / `GetCurrentCell` / `SetCellSelection` / `ClearCellSelection` / `GetCellSelection` / `SetSelectedCells` / `GetSelectedCells` / `IsCellSelected` / `IsCellCurrent`) and cell-selection events (`AttachCurrentCellChanged` / `AttachCellSelectionChanged`, also showing the current cell and the number of selected cells), row-selection events (`AttachSelect` / `AttachSelChanged`, also showing the selected-row count and row indices), the CheckBox checking APIs (`SetSubItemCheck` / `IsSubItemChecked` / `SetDataItemCheck` / `IsDataItemCheck` / `SetCheckedDataItems` / `GetCheckedDataItems`) and `auto_check_select` (`SetAutoCheckSelect` / `IsAutoCheckSelect`). A "Copy & Export" group demonstrates `CopySelectionToClipboard(true)` (copy as CSV), `ExportToCsvFile(path, false)` (export whole table) and the `SetEnableCopy` / `SetEnableCsvExport` toggles. A "Progress & Editor" group demonstrates runtime switching of `progress_text_pos` / `progress_color` (with `SetSubItemProgressById` to change a single cell's progress) and `SetColumnEditorTypeById` to switch a column's editor type (text / number / date / combo). An "Event & State" group demonstrates custom sorting via `SetSortCompareFunction` and the edit state via `AttachEnterEdit` / `AttachLeaveEdit`. Column references in the on-screen labels and message boxes are shown as the column index (ColumnIndex) rather than the column ID.

#### 1.3 Cell word wrap (Report view)

| Capability | API | Description |
|-----------|-----|-------------|
| Cell single/multi-line (word wrap) | `SetSubItemSingleLine(ById)` / `IsSubItemSingleLine(ById)` | Controls whether a Report cell's text is single-line (`true`, default, ellipsis on overflow) or multi-line (`false`, word wrap by the cell's width); the row height must be enlarged by the caller via `SetDataItemHeight`, otherwise the overflow is clipped |

Implementation note: the Report view is virtual, so its cell controls are reused while scrolling; therefore the single/multi-line property is stored in the data model (the `TEXT_SINGLELINE` bit of `nTextFormat`) and applied by the framework **when filling the cell data** onto the reused control (reusing the existing per-cell text-format path, with no new struct field). Wrapping in the List / Icon views is controlled by their own `SetTextSingleLine`; this API is Report-only (in non-Report views `Set*` returns `false` and `Is*` returns `true`).

#### 1.4 Column-level compare mode (sorting)

| Capability | API / flags | Description |
|-----------|-------------|-------------|
| Column-level compare mode | `SetColumnSortFlag(ById)` / `GetColumnSortFlag(ById)`, flags in `ListCtrlSubItemSortFlag` | Declares the comparison mode per column; clicking that column's header sorts by it automatically. Determined by the column's semantics, replacing the earlier "infer from the cell's `nProgress`" behavior |

Flags (`enum ListCtrlSubItemSortFlag`, bitwise-combinable): `kSortByGroup` (group by `nSortGroup` first), `kSortNoCase` (case-insensitive strings), `kSortByText` (default, lexicographic text), `kSortByTextAsNumber` (numeric text, `"10" > "9"`), `kSortByTextAsDate` (chronological text compare, e.g. `"2024-3-7" < "2024-10-1"`), `kSortByUserDataN` / `kSortByUserDataS` (by user data), `kSortByProgress` (by progress value `nProgress`).

Implementation note: the per-column flag is stored in `ListCtrl::m_columnSortFlagMap` (column ID -> `uint8_t`); both header-click sorting (`OnColumnSorted`) and programmatic sorting (`SortDataItemsById`) read/write it, so the app only declares it once. The `SortDataCompareFunc` inference branch ("sort by progress when any cell has `nProgress >= 0`") has been removed and replaced by the explicit `kSortByProgress` declaration.

Demo: in `examples/ListCtrl`, column 2 (the progress column) declares `kSortByProgress`, column 4 holds pure numeric text and declares `kSortByTextAsNumber`, and column 5 holds date text (not zero-padded, e.g. `2020-3-7`) and declares `kSortByTextAsDate`; click the respective header to see progress / numeric / date sorting.

Date mode (`kSortByTextAsDate`): parses the text into a comparable 64-bit key by taking the "year, month, day, hour, minute, second" numeric fields in order; fields may be separated by any non-digit characters and month/day/hour need not be zero-padded (e.g. `2024-3-7`, `2024/03/07`, `2024-03-07 13:45:00`). Text that cannot be parsed as a date is treated as the minimum value (consistent with the "invalid value is smallest" convention of the other flags), and equal keys fall back to a text compare, guaranteeing a strict total order.

> Note: only single-column sorting is supported, and it is a full-table sort with a full refresh; incremental / partial sorting was decided to be **cancelled (not implemented)** after review.

With no item selected, arrow keys fall back to scrolling (intended, not a defect) |

Note the XML attribute is `auto_tooltip` (not `auto_show_tooltip`) |

#### 1.7 Variable row height / text ellipsis (existing)

| Capability | Implementation | Description |
|-----------|----------------|-------------|
| Variable row height | `ListCtrl::SetDataItemHeight` (default row height) / `SetDataItemHeight(itemIndex, ...)` (per-row height) | Supports a uniform row height and per-row heights; the existing demo already showcases it |

### 3. Candidate optimizations (to evaluate / to verify / architectural)

| # | Item | Status | Description |
|---|------|--------|-------------|
| P1 | Heap-allocation overhead of cell storage | Completed (Phases 0–3 all done and accepted in Release plus the Debug assertion verified; Phase 4 verified as not needed) | In the data model `ListCtrlData`, cell storage uses `std::shared_ptr` (`StoragePtr` / `StoragePtrList` / `StorageMap`), i.e. each cell is a separate heap allocation, actually ~130B+ per cell on x64; at large scale this leads to noticeable memory use, allocation overhead and fragmentation. Consider contiguous per-column storage (`std::vector<ListCtrlSubItemData2>`) or splitting sparse fields (progress / rich text) into an SoA layout, expected to save 30%+ of memory. The storage refactor has started (design: [ListCtrl存储重构设计方案.md](misc/ListCtrl存储重构设计方案.md)): **Phase 1 "identity/position split" is done** (introducing `RowId` + `m_displayOrder`, with the column/row-attribute pools indexed by RowId), removing the O(N×C) shifting on middle insert/delete and the full-column deep copy on sort; **Phase 2 "contiguous paged storage" done and accepted** (the column pool changed from `std::vector<std::shared_ptr<Storage>>` to `std::vector<std::unique_ptr<StoragePage>>` contiguous paged storage, page size 64, lazily allocated, and `Storage` usage points uniformly access by `(RowId → const Storage*)`; the code is complete and compiles, and all Release measurements passed and the Debug `AssertDataConsistency()` assertion reported no failure: `SetDataItemCount` regression fixed 23.2→2.7 ms, cell fill 1425.8→1204.8 ms, insert/delete/sort flat or slightly better, scroll repaint 13.020→11.032 ms/frame, dense peak memory 174.0→131.2 MB (↓24.6%), sparse 67.0→52.0 MB not inflated), delivering the memory reduction target above; | P2 | Column-major storage vs. row-major access traversal overhead | Done (compiles for Debug\|x64; **Release same-session A/B: mean 13.804 → 13.300 ms/frame, 3.7% faster, no regression**) | **Conclusion: no storage-layout change was needed; only a local de-allocation was done**. After Phase 1/2, `GetSubItemStorageList(itemIndex)` merely performs N `GetStorageAt` calls over `m_dataMap` (column -> page list) (`page = RowId / 64`, `slot = RowId % 64`, O(1) pointer positioning) and pushes them into a small vector; that is not a bottleneck by itself, so **there is no need to switch to row-major storage or add a row-major cache**. Minimal change implemented (local, low risk, revertible, no public interface or data-model change): (1) `ListCtrlReportView::FillDataItem` no longer builds the on-the-spot `std::map<size_t, const Storage*> subItemDataMap` per row (it only did N lookups by `columnId`, i.e. N red-black-tree node allocations + N O(log N) lookups + a deallocation per row); it now uses a linear search over `subItemList` (N <= ~10, contiguous memory, zero allocation); (2) added `reserve()` for that function's `elementDataList` and `subItemPtrList` vectors. **Release same-session A/B measurement (scroll repaint, 20 frames per run, 3 runs each)**: before 14.657 / 13.807 / 12.947 (mean **13.804**); after 13.130 / 13.141 / 13.670 (mean **13.300**) -> about **0.50 ms per frame saved (-3.7%)**, matching the estimated "a few percent", with smaller run-to-run spread after the change (range 0.54 vs 1.71), **no regression** |
| P3 | Maximum horizontal scroll range with frozen columns | Verified (no change needed) | Conclusion: **the scroll range is already correct; no frozen-width deduction is needed**. The content width comes from `ListCtrlReportLayout::ArrangeChildren`'s `sz.cx = max(GetItemWidth(), rc.Width())`, where `GetItemWidth()` -> `ListCtrlReportView::GetListCtrlWidth()` **sums all visible column widths (including frozen ones)** (`EstimateLayoutSize` is only for `auto` sizing and `CalcEstimateSize` is a H/VTile helper, neither participates in the horizontal extent); the scroll range is computed by `ScrollBox::NeedShowHScrollBar()` as `max(content width - viewport width, 0)`, and the "viewport width" there is also the **full width including the frozen region**. Let total column width be `W`, viewport width `V` and frozen width `F`: max scroll is then `W - V`; on the paint side the non-frozen pass aligns both the clip left edge and the content origin to `viewport.left + F` (`rcClip.left = rcViewport.left + nFrozenWidth`, `rcNewPaint.left = rcViewport.left + nFrozenWidth + scrollPos.cx`), so at scroll 0 the first non-frozen column's left edge sits exactly at `viewport.left + F`, flush against the frozen region, and at `W - V` the last column's right edge lands exactly on `viewport.right` - the frozen width cancels out in both formulas, making `W - V` the correct upper bound with no explicit deduction required and no occlusion or blank strip (the part hidden behind the frozen columns is excluded from painting via `rcNewPaint.left`). Hands-on UI testing also found no anomaly with frozen columns |
| P4 | Re-arrange on every paint | Verified (no change needed) | `ListCtrlReportView::PaintChild` does call `ReArrangeChild(false)` on every paint, but that call is guarded internally by `VirtualLayout::NeedReArrange()`: `ListCtrlReportLayout::NeedReArrange()` is true only when "the scroll position differs from the applied virtual offset" (`GetScrollPos().cy != GetScrollVirtualOffset().cy`), so it returns immediately during ordinary repaints with **no re-arrange cost**; size / data changes go through the forced `ReArrangeChild(true)` path in `Refresh()`. The "each control painted twice" in the frozen-column case happens only when `frozen_column_count > 0` (single pass without frozen columns) and is inherent to two-pass frozen-column clipping, not redundant painting |

| A2 | Layout model upgrade (multi-level headers / cell merge / in-table tree / row group collapse) | Wrapped up (stages C0 / C1 / C1b done; C4–C7 cancelled) | Requires an upgrade of the header and row layout model; **C4–C7 (cell merge / in-table tree and row group collapse / multi-level header / row drag reorder) were decided NOT to be implemented after review** — all four require an overall upgrade of the header and row layout model, with too large a change surface, so they are cancelled and A2 is wrapped up here (see the [Cancelled] annotations on each stage in design doc §3) |
