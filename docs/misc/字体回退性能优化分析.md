# 字体回退性能优化分析（覆盖全部文本测量/绘制路径）

分析对象：`duilib/RenderSkia` 下的文本测量与绘制实现，以及 `Core/FontManager.cpp` 的回退字体管理。
目标：在支持 GB18030（会出现大量生僻字、Emoji）的前提下，保证绘制文字时界面不卡顿。
范围：**除"字符→字体/字形"结果缓存之外的优化方案**。缓存类方案的现状问题放在第五节单列，作为前置风险说明。

---

## 一、结论摘要

字体回退的耗时可以拆成四个乘数：

```
回退总耗时 ≈ 单字符解析成本 × 文本字符数 × 单字符解析次数(测量/绘制/重复布局) × 未命中候选字体数
```

现有实现的四个乘数都存在放大：

1. **解析次数被放大**：同一段文本在一次界面刷新中往往被断行/测量/绘制多次，每次都对所有字符重新做一次"字符 → 字形 → 回退字体"解析。最坏情况下（默认横向路径 + 居中对齐 + 省略号），一个生僻字每帧会被解析 4 次以上。
2. **单字符成本高**：每次解析都伴随 `std::function` 构造/拷贝、`dynamic_cast`、虚函数调用、容器分配、`unordered_map` 查找，以及候选字体链的线性扫描。
3. **候选字体扫描没有提前退出**：理论上有相当数量的码点可能没有任何字体覆盖（例如 Unicode 未分配码点），现有实现会为这类码点把整条候选字体链都创建并检查一遍。（评估结论：实际绘制的都是真实存在的文本，该场景基本不会出现，见 4.3，决定不做。）
4. **绘制是逐字符的**：每个字一次 `unicharToGlyph` + 一次 `getWidthsBounds` + 一次 `drawGlyphs`，没有按"同字体连续字符段（run）"批量提交。

因此，除了补缓存，收益最大的方向是：**一次解析、两阶段复用**（布局阶段算出的字体/字形直接给绘制阶段用）、**run 级批量绘制**、**消除热路径固定开销**、**减少测量/布局轮次**。

## 二、文本路径全景（之前只分析了其中一条）

`duilib` 的文本测量与绘制由 **5 个实现模块**（`SkTextBox`、`HorizontalDrawText`、`VerticalDrawText`、`DrawRichText`、`DrawSkiaText` 公共层）组合出 **7 条实际路径**。入口都汇聚到 `Render_Skia::DrawString` / `Render_Skia::MeasureString` / 富文本接口。

### 2.1 路径总表

| 编号 | 路径 | 触发条件 | 测量实现 | 绘制实现 | 单字符回退解析次数（每帧） |
| --- | --- | --- | --- | --- | --- |
| P1 | 默认横向文本 | 非纵向、无两端对齐、无字间距 | `SkTextBox` → `Linebreak` → `BreakText` | `SkTextBox` → 逐行 `DrawSimpleText` → 逐字符 | 2 ~ 4 次 |
| P2 | 两端对齐 / 有字间距的横向文本 | `TEXT_HJUSTIFY` 或 `fWordSpacing > 0` | `HorizontalDrawText` 逐字符 `MeasureTextChar` | `HorizontalDrawText` 逐字符 `DrawSimpleText` | 2 次（测量 + 绘制各算一遍） |
| P3 | 纵向文本 | `TEXT_VERTICAL` | `VerticalDrawText` 逐字符 `MeasureTextChar` | `VerticalDrawText` 逐字符 `DrawSimpleText` | 2 次 |
| P4 | 富文本布局 | `MeasureRichText` / `CreateDrawRichTextCache` | `DrawRichText::InternalDrawRichText` 按 run 调 `BreakText` | 布局阶段不绘制 | 1 次（布局时） |
| P5 | 富文本绘制（缓存有效） | `DrawRichTextCacheData` | 无（应使用缓存） | `DrawTextRun` → `DrawTextString` → `SkTextBox` 重新断行 | 1 ~ 2 次（每帧重新解析） |
| P6 | 富文本绘制的字间距分支 | `m_fLetterSpacing + m_fJustifySpacing > 0` | `DrawTextRun` 逐字符 `MeasureTextChar` | `DrawTextRun` 逐字符 `DrawSimpleText` | 2 次（每帧） |
| P7 | 多行文本测量 | `MeasureString`（非单行） | `CountLines`（逐行 `Linebreak`）+ 逐行 `MeasureText` | — | 2 次（测量阶段） |

### 2.2 入口分发

```cpp
// Render_Skia.cpp
DrawString():
  ├─ TEXT_VERTICAL                              → VerticalDrawText        (P3)
  ├─ TEXT_HJUSTIFY || fWordSpacing > 0.0001f    → HorizontalDrawText      (P2)
  └─ 其他                                       → SkTextBox               (P1)

MeasureString():
  ├─ TEXT_VERTICAL                              → VerticalDrawText        (P3)
  ├─ TEXT_HJUSTIFY || fWordSpacing > 0.0001f    → HorizontalDrawText      (P2)
  └─ 其他                                       → 单行 MeasureText / 多行 CountLines+MeasureText (P1/P7)
```

对应代码：[Render_Skia.cpp#L1547-L1688](file:///e:/develop/nim_duilib/duilib/RenderSkia/Render_Skia.cpp#L1547-L1688)、[Render_Skia.cpp#L1690-L1840](file:///e:/develop/nim_duilib/duilib/RenderSkia/Render_Skia.cpp#L1690-L1840)。

**注意**：绝大多数控件（Label、CheckBox、Button、TabCtrl、ListCtrl、Calendar、Marquee、Switch、Stepper 等，共数十处）走的是 **P1（SkTextBox）**，而不是 P2。因此性能优化的主战场是 P1，其次才是 P2/P3；富文本是 P4/P5/P6。

### 2.3 控件层的叠加

控件的 `OnPaint` 中通常"先 `MeasureString`、再 `DrawString`"，例如
[LabelImpl.cpp#L735-L759](file:///e:/develop/nim_duilib/duilib/Control/LabelImpl.cpp#L735-L759)、
[TabCtrl.cpp#L3127-L3130](file:///e:/develop/nim_duilib/duilib/Control/TabCtrl.cpp#L3127-L3130)、
[Switch.cpp#L527-L549](file:///e:/develop/nim_duilib/duilib/Control/Switch.cpp#L527-L549)、
[Marquee.cpp#L256-L358](file:///e:/develop/nim_duilib/duilib/Control/Marquee.cpp#L256-L358)；
[CheckBox.h#L975-L1007](file:///e:/develop/nim_duilib/duilib/Control/CheckBox.h#L975-L1007) 则是每次绘制直接调用 `DrawString`。

也就是说 P1/P7 的解析次数会在"测量 + 绘制"两轮里各发生一次，且每次重绘都会重复。富文本路径由 `TextDrawer` 做了文本级缓存（[TextDrawer.cpp#L179-L207](file:///e:/develop/nim_duilib/duilib/Control/TextDrawer.cpp#L179-L207)），`Marquee` 也做了测量缓存，但普通文本控件没有对应缓存。

## 三、逐路径问题与优化点

### 3.1 P1：默认横向路径（SkTextBox）——主战场

#### 现状调用链

```
Render_Skia::DrawString
└─ SkTextBox::Draw
   └─ SkTextBox::Visit                      // SkTextBox.cpp#L122-L253
      ├─ [纵向对齐≠顶部] DrawSkiaText::CountLines    // 逐行 Linebreak → BreakText
      ├─ 每行: DrawSkiaText::Linebreak → BreakText   // 每行一次全量字形转换
      ├─ [水平对齐≠左] DrawSkiaText::MeasureText     // 每行再一次全量字形转换
      └─ CanvasVisitor → TextBox_DrawText           // SkTextBox.cpp#L428-L523
         ├─ [省略号/下划线/删除线] MeasureText / BreakText  // 再算一次
         └─ DrawSkiaText::DrawSimpleText(textData)   // 逐字符绘制
            └─ GetDrawStringUTF32 → 逐字符 DrawSimpleText
               └─ unicharToGlyph → [回退解析] → DrawSkGlyphChar
```

关键代码：
- [SkTextBox.cpp#L122-L253](file:///e:/develop/nim_duilib/duilib/RenderSkia/SkTextBox.cpp#L122-L253)
- [SkTextBox.cpp#L428-L523](file:///e:/develop/nim_duilib/duilib/RenderSkia/SkTextBox.cpp#L428-L523)
- [DrawSkiaText.cpp#L380-L409](file:///e:/develop/nim_duilib/duilib/RenderSkia/DrawSkiaText.cpp#L380-L409)

#### 问题

1. **同一行文本被断行多次**：
   - 纵向居中/底部对齐时，`CountLines` 先把整段文本逐行 `BreakText` 一遍（[SkTextBox.cpp#L172-L177](file:///e:/develop/nim_duilib/duilib/RenderSkia/SkTextBox.cpp#L172-L177)）；
   - 随后 `Visit` 循环里每行再 `Linebreak` 一次（[SkTextBox.cpp#L204-L207](file:///e:/develop/nim_duilib/duilib/RenderSkia/SkTextBox.cpp#L204-L207)）；
   - 水平居中/右对齐时，每行再 `MeasureText` 一次（[SkTextBox.cpp#L216-L219](file:///e:/develop/nim_duilib/duilib/RenderSkia/SkTextBox.cpp#L216-L219)）；
   - 有省略号时，`TextBox_DrawText` 里还会 `MeasureText` + `EllipsisText`（内部再 `BreakText`）（[SkTextBox.cpp#L455-L522](file:///e:/develop/nim_duilib/duilib/RenderSkia/SkTextBox.cpp#L455-L522)）。
   
   每一次 `BreakText` 都会对整行执行 `unicharsToGlyphs`，并对 `glyphID == 0` 的字符逐个调用回退解析（[DrawSkiaText.cpp#L481-L491](file:///e:/develop/nim_duilib/duilib/RenderSkia/DrawSkiaText.cpp#L481-L491)）。**生僻字在这种路径下每帧被解析 3~4 次。**

2. **绘制阶段重复做布局做过的事**：`DrawSimpleText(textData)` 内部把整行再转成 UTF32，然后逐字符 `unicharToGlyph` + 回退解析 + `getWidthsBounds` + `drawGlyphs`，而 `BreakText` 刚才已经算过 glyph 和宽度。

3. **每行一次 `GetDrawStringUTF32`**：`DString text = strText;` + 3 次 `ReplaceAll` + UTF16→UTF32 转换（[HorizontalDrawText.cpp#L24-L41](file:///e:/develop/nim_duilib/duilib/RenderSkia/HorizontalDrawText.cpp#L24-L41) 为同款实现，`DrawSkiaText::GetDrawStringUTF32` 见 [DrawSkiaText.cpp#L53-L70](file:///e:/develop/nim_duilib/duilib/RenderSkia/DrawSkiaText.cpp#L53-L70)）。

#### 优化

- **A1：`CountLines` 与 `Linebreak` 结果复用**。`CountLines` 已经拿到了每行字节长度，`Visit` 循环完全可以复用它，不必再断行一次；或者让 `Visit` 自己收集行信息，纵向对齐在收集完之后再算。
- **A2：断行、测量、对齐合并为一次**。`BreakText` 已经返回每行 `glyphWidths`，水平居中/右对齐的行宽可以直接累加得到，无需再 `MeasureText` 一次。
- **A3：把 `BreakText` 的结果（glyphID 列表 + 字体 + 位置）装进 `visitor` 参数**，绘制阶段直接 `drawGlyphs`，不再逐字符解析。
- **A4：省略号场景只做一次断行**：先按"预留省略号宽度"断行一次，避免"先测宽度、再断行"两轮。

### 3.2 P2：两端对齐 / 字间距路径（HorizontalDrawText）

#### 现状

- 测量：[HorizontalDrawText.cpp#L53-L104](file:///e:/develop/nim_duilib/duilib/RenderSkia/HorizontalDrawText.cpp#L53-L104) 逐字符 `MeasureTextChar`（内部做回退解析）。
- 绘制：[HorizontalDrawText.cpp#L640-L730](file:///e:/develop/nim_duilib/duilib/RenderSkia/HorizontalDrawText.cpp#L640-L730) 逐字符 `DrawSimpleText`（再做一次回退解析）。
- 额外：`CalculateDefaultCharWidth` 还会对 `'A'` 单独测量一次（[HorizontalDrawText.cpp#L281-L305](file:///e:/develop/nim_duilib/duilib/RenderSkia/HorizontalDrawText.cpp#L281-L305)），测量和绘制各一次。
- 每次调用都重新执行 `GetDrawStringUTF32`（[HorizontalDrawText.cpp#L24-L41](file:///e:/develop/nim_duilib/duilib/RenderSkia/HorizontalDrawText.cpp#L24-L41)）。

#### 问题

1. `MeasureTextChar(pFont)` 版本**每字符构造一个 `std::function`**（[DrawSkiaText.cpp#L78-L104](file:///e:/develop/nim_duilib/duilib/RenderSkia/DrawSkiaText.cpp#L78-L104)），随后又按值传给内部重载。`DrawSimpleText(pFont)` 同样每字符构造一次（[DrawSkiaText.cpp#L317-L333](file:///e:/develop/nim_duilib/duilib/RenderSkia/DrawSkiaText.cpp#L317-L333)）。
2. `THorizontalChar` 结构只保存了 `ch / size / bounds`，**没有保存该字符实际命中的回退字体**（[HorizontalDrawText.cpp#L45-L51](file:///e:/develop/nim_duilib/duilib/RenderSkia/HorizontalDrawText.cpp#L45-L51)），导致绘制阶段必须重新解析。
3. 空白字符会触发第二次测量（[HorizontalDrawText.cpp#L91-L96](file:///e:/develop/nim_duilib/duilib/RenderSkia/HorizontalDrawText.cpp#L91-L96)），其中包含一次 `MeasureTextChar('A')`。
4. 测量与绘制都完整跑一遍 `CalculateTextCharBounds` + `CalculateHorizontalTextBounds`。

#### 优化

- **B1：`THorizontalChar` 增加 `const SkFont*`（或 `IFont*`）+ `SkGlyphID`**，测量阶段解析一次，绘制阶段直接使用。
- **B2：整行先批量 `unicharsToGlyphs`**（一次调用），再只对 `glyph == 0` 的字符走回退解析，避免逐字符 `unicharToGlyph`。
- **B3：绘制改为按"同字体连续段（run）"批量 `drawGlyphs`**，宽度直接取 `THorizontalChar.size.width`，不再调用 `getWidthsBounds`。
- **B4：空白/控制字符提前返回**，不进入回退流程，也不做 `'A'` 的二次测量（`'A'` 宽度可在首次算好后复用）。

### 3.3 P3：纵向路径（VerticalDrawText）

#### 现状与问题

- 测量：[VerticalDrawText.cpp#L84-L150](file:///e:/develop/nim_duilib/duilib/RenderSkia/VerticalDrawText.cpp#L84-L150) 逐字符 `MeasureTextChar`。
- 绘制：[VerticalDrawText.cpp#L660-L840](file:///e:/develop/nim_duilib/duilib/RenderSkia/VerticalDrawText.cpp#L660-L840) 逐字符 `DrawSimpleText`；旋转字符每个都要 `save/translate/rotate/restore`。
- `TVerticalChar` 同样不保存命中的回退字体（[VerticalDrawText.cpp#L75-L82](file:///e:/develop/nim_duilib/duilib/RenderSkia/VerticalDrawText.cpp#L75-L82)）。
- 与 P2 相同的 `std::function`/重复解析/默认字符二次测量问题。

#### 优化

- **C1**：同 B1、B2，布局阶段携带字体与字形。
- **C2**：旋转字符与非旋转字符分别成 run；同一角度的连续字符可合并为一次 `drawGlyphs`（使用 `SkCanvas::save/rotate` 包住整段 run，而不是每字符一次）。
- **C3**：纵向路径目前只在 `TEXT_VERTICAL` 时使用，调用频率低于 P1，优先级可放在 P2 之后。

### 3.4 P4：富文本布局（DrawRichText::InternalDrawRichText）

#### 现状

- 每个文本 run 调一次 `BreakText`（[DrawRichText.cpp#L641-L646](file:///e:/develop/nim_duilib/duilib/RenderSkia/DrawRichText.cpp#L641-L646)），内部已是"批量字形转换 + 逐个回退字符解析"。
- 断行结果中的 `glyphIDs / glyphWidths` **只被用于计数**：`m_nGlyphCount = breakTextData.glyphIDs.size()`（[DrawRichText.cpp#L742](file:///e:/develop/nim_duilib/duilib/RenderSkia/DrawRichText.cpp#L742)），`TPendingDrawRichText` 中只保存 `m_textView / m_destRect / m_spFont`（[DrawRichText.cpp#L25-L64](file:///e:/develop/nim_duilib/duilib/RenderSkia/DrawRichText.cpp#L25-L64)）。
- 每个 run 若字体与前一个不同，会 `pRenderFactory->CreateIFont()` + `InitFont`（[DrawRichText.cpp#L380-L408](file:///e:/develop/nim_duilib/duilib/RenderSkia/DrawRichText.cpp#L380-L408)）。DC 场景下这是每个布局一次。

#### 问题

1. **布局算出的字形结果被丢弃**，绘制阶段只能重算（见 P5）。
2. **逐字符 `getWidthsBounds` 的回退分支**：`BreakText` 对 `glyph == 0` 的字符逐个调用回退解析，并逐个 `getWidthsBounds(1)`（[DrawSkiaText.cpp#L481-L491](file:///e:/develop/nim_duilib/duilib/RenderSkia/DrawSkiaText.cpp#L481-L491)）。
3. `CreateIFont` + `InitFont` 的对象创建虽然轻量（`SkFont` 懒创建），但会带来一次 `shared_ptr` 分配和一次 `dynamic_cast`（`Font_Skia::GetFontHandle`，[Font_Skia.cpp#L49-L60](file:///e:/develop/nim_duilib/duilib/RenderSkia/Font_Skia.cpp#L49-L60)）。

#### 优化

- **D1：把 `BreakText` 的产物写进 `TPendingDrawRichText`**（`glyphIDs`、`glyphWidths`、`回退字体索引`），布局与绘制分离但数据不丢。
- **D2：`BreakText` 的回退分支批量化**：收集所有 `glyph == 0` 的码点，一次性按字体分组后再批量 `getWidthsBounds`；`CreateFallbackFont` 支持批量码点查询。
- **D3：run 内字体对象复用**：当前只在"与前一个 run 相同"时复用；可改为按 `UiFont` 值做 key 的字体池（这属于缓存，但对象池与字符缓存不同，能显著减少 `CreateIFont` 次数）。

### 3.5 P5：富文本绘制（DrawRichTextCacheData → DrawTextRun）

#### 现状

```
DrawRichTextCacheData                       // DrawRichText.cpp#L1720-L1881
└─ 每个 pending run: DrawTextRun            // DrawRichText.cpp#L1075-L1184
   ├─ fSpacing <= 0 → DrawTextString        // DrawRichText.cpp#L1896-L1980
   │  └─ 新建 SkTextBox → Linebreak/BreakText → 逐字符绘制   // 每帧重新断行！
   └─ fSpacing > 0  → 逐字符 MeasureTextChar + 逐字符 DrawSimpleText
```

#### 问题

1. **富文本缓存"只缓存了布局矩形，没有缓存字形"**：`DrawTextString` 每次都重新构造 `SkTextBox` 并执行 `Linebreak`，即每帧对每个 run 重新做一次 `unicharsToGlyphs` + 回退解析。缓存只避免了对 `richTextData` 的整体重排，没避免字形解析。
2. **字间距分支每帧每字符解析两次**：`MeasureTextChar`（[DrawRichText.cpp#L1127](file:///e:/develop/nim_duilib/duilib/RenderSkia/DrawRichText.cpp#L1127)）与 `DrawSimpleText`（[DrawRichText.cpp#L1178-L1180](file:///e:/develop/nim_duilib/duilib/RenderSkia/DrawRichText.cpp#L1178-L1180)）。
3. 每个 run 都会 `dynamic_cast<Font_Skia*>`（[DrawRichText.cpp#L1091](file:///e:/develop/nim_duilib/duilib/RenderSkia/DrawRichText.cpp#L1091)、[DrawRichText.cpp#L1905](file:///e:/develop/nim_duilib/duilib/RenderSkia/DrawRichText.cpp#L1905)）。

#### 优化

- **E1：缓存中保存 glyph run（字体 + glyphID 数组 + 起点坐标/宽度）**，绘制时一次 `drawGlyphs`，完全跳过断行与 `unicharToGlyph`。这是富文本路径收益最大的改动。
- **E2：字间距分支复用 E1 的 run**，只在 run 内按 `fSpacing` 调整坐标，避免重新测量。
- **E3：省略号分支复用断行结果**（当前 `TEXT_END_ELLIPSIS` 会触发 `SkTextBox` 内部的重新测量/断行，[DrawRichText.cpp#L1856-L1865](file:///e:/develop/nim_duilib/duilib/RenderSkia/DrawRichText.cpp#L1856-L1865)）。

### 3.6 P6：富文本字间距/两端对齐分支

即 `DrawTextRun` 的 `fSpacing > 0` 分支，见 3.5 第 2 点。另外 `m_fJustifySpacing` 会让几乎所有段落走这个分支，因此它不是少数场景，而是富文本两端对齐时的默认路径。

### 3.7 P7：多行测量（MeasureString）

#### 现状

`Render_Skia::MeasureString` 非单行时：
1. `CountLines` → 内部逐行 `Linebreak` → `BreakText`（[Render_Skia.cpp#L1794-L1801](file:///e:/develop/nim_duilib/duilib/RenderSkia/Render_Skia.cpp#L1794-L1801)、[DrawSkiaText.cpp#L691-L710](file:///e:/develop/nim_duilib/duilib/RenderSkia/DrawSkiaText.cpp#L691-L710)）；
2. 再逐行 `MeasureText`，**又做一遍 `unicharsToGlyphs` + 回退解析**（[Render_Skia.cpp#L1809-L1823](file:///e:/develop/nim_duilib/duilib/RenderSkia/Render_Skia.cpp#L1809-L1823)）。

#### 优化

- **F1：`CountLines` 同时返回每行的"宽度/最大宽度"**，测量阶段直接使用，去掉第二轮 `MeasureText`。
- **F2：单行路径的 `MeasureText` 已有快速通道**（无回退时直接 `font.measureText`，[DrawSkiaText.cpp#L209-L221](file:///e:/develop/nim_duilib/duilib/RenderSkia/DrawSkiaText.cpp#L209-L221)），可把同样的"整行无回退"快速判定提到调用方：先用一次 `unicharsToGlyphs` 判断整行是否全部命中主字体，命中则一条路径走到底。

## 四、跨路径共性优化（不依赖缓存）

### 4.1 一次解析、两阶段复用

**现状**：解析结果只存在于栈上的临时变量里，测量结束即丢弃；绘制阶段重新解析。P1~P7 都存在这个问题。

**建议**：引入一个轻量的"文本运行结果"结构，由测量/布局阶段产出、绘制阶段消费：

```cpp
struct TextGlyphRun
{
    const IFont*     m_pFont = nullptr;   //命中的字体（含回退字体）
    SkFont*          m_pSkFont = nullptr; //字体句柄（可选，便于直接绘制）
    const SkGlyphID* m_pGlyphs = nullptr; //字形数组（批量）
    const SkScalar*  m_pAdvances = nullptr;
    SkScalar         m_x = 0;             //run 起点
    SkScalar         m_y = 0;
    uint32_t         m_nCount = 0;
    bool             m_bRotate90 = false; //纵向路径使用
};
```

**收益**：把"每字符解析次数"从 2~4 次降到 1 次。
**风险**：需要同时改测量与绘制两侧，`THorizontalChar / TVerticalChar / TPendingDrawRichText` 的生命周期要跟着缓存走。

### 4.2 run 级批量绘制

**现状**：`DrawSkGlyphChar` 每个字符一次 `getWidthsBounds` + 一次 `drawGlyphs`（[DrawSkiaText.cpp#L294-L315](file:///e:/develop/nim_duilib/duilib/RenderSkia/DrawSkiaText.cpp#L294-L315)），并调用一次 `iswspace`。

**优化**：
1. 连续同字体的字符合并为一次 `drawGlyphs(glyphSpan, pointSpan, ...)`（或使用 `SkTextBlob`）。
2. 宽度/边界在布局阶段已经算过，绘制阶段**不再调用 `getWidthsBounds`**；只有"占位方框"兜底才需要。
3. `iswspace` 换成内联判断（ASCII 范围直接比较，非 ASCII 用固定表）。
4. 纵向旋转字符：同角度的连续字符共用一次 `save/rotate/restore`。

**注意事项**：
- 现有逐字符绘制带有"越界不画 / 末尾省略号"逻辑（[HorizontalDrawText.cpp#L684-L720](file:///e:/develop/nim_duilib/duilib/RenderSkia/HorizontalDrawText.cpp#L684-L720)），批量时要先按可见区间裁剪 run。
- `glyph == 0` 的兜底方框需要单独处理，不能混进正常 run。

### 4.3 提前退出与快速判定（处理结论：不做）

> **处理结论：不实施。** 实际使用场景中绘制的内容都是真实存在的文本（界面文案、用户输入、业务数据），"所有候选字体都不支持某个码点"的最坏路径在真实业务中基本不会出现，为此引入额外判定逻辑与维护成本不划算。
>
> 以下内容仅作为分析记录保留，不进入实施计划；其中的"覆盖索引"思路仍可在 4.5 中独立评估。

这是 GB18030 场景下最容易忽略、但收益很直接的一项。**但"提前退出"的判定依据必须是语言无关的，否则会误伤其他语种。** GB18030 只是触发该问题的一个例子，同样的最坏路径会出现在藏文、蒙古文、彝文、泰文、天城文、阿拉伯文、Emoji 等任何"主字体不覆盖"的文本上。

#### 4.3.1 安全的做法（未采纳，仅供参考）

1. **结构性非法码点硬拒绝**：只拒绝与 Unicode 版本无关、任何字体都不可能有字形的码点——
   - 超出 Unicode 范围（> U+10FFFF）；
   - 代理区（U+D800 ~ U+DFFF，UTF-32 中不应出现）；
   - 非字符（U+FDD0 ~ U+FDEF，以及每个平面末尾的 U+FFFE / U+FFFF）。
   
   这类判定不依赖"Unicode 是否已分配"，不会随版本升级失效。
2. **每字体覆盖索引（权威判定）**：从字体自身的 cmap 构建覆盖表（BMP 用位图，补充平面用有序区间表，见 4.5），"这个字符能不能显示"由字体的实际覆盖决定，而不是由静态表决定。语言无关、Unicode 版本无关；这是 4.3 中真正能"提前退出"的部分。
3. **ASCII / 空白的"减负"而非"跳过"**：`ch < 0x80`、空格、制表符等只用于**跳过候选链的准备工作**（`std::function` 构造、`dynamic_cast`、容器分配），**仍然要执行主字体的字形判定**。原因：存在只含 CJK 的字体、符号字体（Wingdings 类）、图标字体，它们可能真的没有 ASCII 字形，直接跳过会画出豆腐块。
4. **零宽/默认可忽略字符**：变体选择符（U+FE00~U+FE0F）、ZWJ/ZWNJ、组合记号等应"不绘制"而不是"回退失败"。判定方式建议用"字形为 0 且 advance 为 0"，避免维护 Unicode 属性表。
5. **区段/脚本只用于排序**：按脚本或区块给候选字体排序、缩小优先查找范围可以，但**失败后必须回退到全量候选搜索**，不能把分组当作排除条件。

#### 4.3.2 不安全的做法（不建议采用）

1. **"Unicode 已分配区段表"作为否定闸门（高风险）**：
   - 依赖 Unicode 版本：CJK 扩展 I（U+2EBF0 起）是 Unicode 15.1 才加入的，16.0 及以后还会继续新增；静态表必然滞后，滞后期间新字符会被判为"无字形"。
   - 与语言无关性冲突：除了 CJK，还有藏文、蒙古文、彝文、泰文、天城文、阿拉伯文等，静态表需要覆盖所有语种的全部新增区块，维护成本高且容易漏。
   - 结论：**不要把它作为"返回 nullptr"的硬判定**。它的收益（跳过无字体可显示的码点）可以由 4.3.1 的覆盖索引以更正确的方式获得。
2. **PUA（U+E000~U+F8FF 等）一律拒绝（高风险）**：
   - 图标字体、符号字体大量使用 PUA 映射字形；
   - GB18030/GBK 的历史实现中存在将生僻字映射到 PUA 的字体（用户自定义区）；
   - 一律拒绝会直接导致这些字体"突然不显示"。
3. **按区段排除候选字体（中风险）**：字符的脚本归属不是"哪个字体覆盖它"的充分条件——中日韩字体常带拉丁字形，符号字体可能覆盖多脚本；标点、数字、组合记号属于 Common/Inherited，可能出现在任意分组。只能用于排序，不能用于排除。

#### 4.3.3 误判的后果与验证

- 误判后果**不是崩溃，而是文字缺失或豆腐块**，且往往只在特定语种、特定字体下暴露，属于用户可见的正确性问题，测试成本高于稳定性问题。
- 必须覆盖的测试语种/场景：中日韩常用字 + CJK 扩展 B~I、藏文（U+0F00）、蒙古文（U+1800）、彝文（U+A000）、泰文（U+0E00）、天城文（U+0900）、阿拉伯文（含 RTL）、Emoji（ZWJ / 变体选择符 / 肤色修饰）、PUA 图标字体、仅含 CJK 的字体。
- 覆盖索引的失效条件：字体热切换、DPI 缩放、主题切换、运行时注册字体文件后，索引必须重建（与字体缓存版本号绑定），否则同样会误判。

### 4.5 减少候选字体扫描次数

1. **覆盖索引**：为每个 `IFont` 预建"码点覆盖表"——BMP 用 64K 位图（8KB/字体），补充平面用有序区间表（`vector<pair<uint32,uint32>>` + 二分）。判断从"cmap 查表"变为"位测试"或"二分查找"，并且可以一次性判断"该字体是否完全覆盖某段文本"。
   - 与"缓存字形结果"不同：这是**静态索引**，大小固定、不随字符数增长。
2. **候选顺序**：把 GB18030 覆盖最全的字体放在最前（Windows 常见为 `Microsoft YaHei`、`SimSun-ExtB`；Linux 为 `Noto Sans CJK SC`），覆盖率低的字体后移或删掉，缩短平均扫描长度。
3. **首次可用性校验前置**：`HasFontName` 已有哈希缓存（[FontMgr_Skia.cpp#L262-L290](file:///e:/develop/nim_duilib/duilib/RenderSkia/FontMgr_Skia.cpp#L262-L290)），但候选创建循环里仍会为每个候选 `CreateIFont`；可先做覆盖索引判断，再决定是否创建。

### 4.6 减少测量/布局轮次

1. `CountLines` 与 `Linebreak` 合并（P1、P7）。
2. 对齐宽度直接从 `BreakText` 的 `glyphWidths` 累加（P1）。
3. `MeasureString` 与 `DrawString` 合并为一次布局（控件层），或由控件持有布局结果。
4. 省略号场景只断行一次（P1、P5）。

### 4.7 长线方案（评估后可选）

1. **交给 Skia 做字体回退**：`SkFontMgr::matchFamilyStyleCharacter(...)` 直接返回支持该字符的 typeface，Skia 内部对系统字体有索引；可保留现有配置列表作为"优先项"，未命中时再交给系统。
2. **`SkShaper` / `SkParagraph`**：一次性完成 shaping、字体回退、run 划分和批量绘制，是根治方案；但会改变字距、连字、RTL、换行等行为，需要完整回归。
3. **`SkTextBlob` 复用**：内容与样式稳定的文本可复用整行 blob（属于缓存类，列为并列收益项）。

## 五、前置风险：回退缓存的键设计（不处理会抵消其他优化）

虽然本次不展开缓存方案，但有一个问题必须先说明，否则第四节的优化收益会被放大或抵消：

1. **回退字体缓存以 `const IFont*` 指针为键**（[FontManager.h#L175](file:///e:/develop/nim_duilib/duilib/Core/FontManager.h#L175)、[FontManager.cpp#L42](file:///e:/develop/nim_duilib/duilib/Core/FontManager.cpp#L42)）。
2. **富文本的 `IFont` 是临时对象**：`InternalDrawRichText` 中通过 `pRenderFactory->CreateIFont()` 创建，生命周期跟随 `DrawRichTextCache`（[DrawRichText.cpp#L380-L408](file:///e:/develop/nim_duilib/duilib/RenderSkia/DrawRichText.cpp#L380-L408)）。缓存重建时旧字体被释放，但 `m_fallbackFontMap` 中的条目不会被删除。
3. **`OnIFontDataRemoved` 只会清空列表、不会 erase 键**（[FontManager.cpp#L660-L672](file:///e:/develop/nim_duilib/duilib/Core/FontManager.cpp#L660-L672)），而且只有 `FontManager` 自己删除字体时才会调用（[FontManager.cpp#L409](file:///e:/develop/nim_duilib/duilib/Core/FontManager.cpp#L409)、[FontManager.cpp#L441](file:///e:/develop/nim_duilib/duilib/Core/FontManager.cpp#L441)），富文本的临时字体永远不会触发。
4. **后果**：
   - `m_fallbackFontMap` 随富文本布局次数持续增长，条目键悬垂；
   - 新字体对象复用了旧地址时，可能命中"旧字号/旧粗斜体"的回退字体，导致**度量错误**（不只是性能问题）；
   - 每次富文本重新布局都可能重新创建回退字体（缓存实际失效）。

**建议**：回退字体缓存改为以内含完整字体参数的键（字体名 + 字号 + 粗体 + 斜体 + 下划线 + 删除线）或 `UiFont` 的哈希值，而不是 `IFont*`。这与"字符缓存"是不同层的问题，但应在实施第四节的优化之前或同时解决。
